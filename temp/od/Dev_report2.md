# YOLO26n 대체 사람 감지 모델 개발 결과

Oct 15, 2026 · 

로봇 전방 카메라의 사람 감지 모델을 Ultralytics YOLO26n(AGPL-3.0)에서 자체 학습한 DEIM-N 512 KD 모델(Apache-2.0)로 바꿔 10월 15일 Orin에 적용했습니다. 사용 범위인 3 m 이내 정확도는 YOLO26n과 비슷하고, Orin 추론 시간은 기존 운영 설정(YOLO26n FP32) 대비 28% 줄었습니다(3.55 → 2.57 ms). Orin 환경, ZED SDK, 는 그대로 두고 ONNX 파일과 설정만 바꿨습니다.

## 배경과 조건

기존 모델은 AGPL-3.0인 Ultralytics YOLO26n을 사람 데이터로 fine-tune한 것이라, 라이선스 부담이 없는 모델로 바꾸는 것이 목표였습니다. 교체는 아래 조건을 모두 지켜야 했습니다.

- **Orin 환경 유지:** L4T 36.4.7, TensorRT 10.3, ZED SDK 5.1.1을 업그레이드하지 않습니다.
- **wrapper 코드 수정 없음:** 이번 교체에서는 wrapper 코드를 건드리지 않습니다. 그래서 ZED wrapper의 `CUSTOM_YOLOLIKE_BOX_OBJECTS` 모드에 그대로 넣을 수 있게, 기존과 같은 ONNX 입출력 형식(`[1,300,6]`, NMS 없음)으로 export합니다.
- **사용 범위:** 전방 카메라 기준 약 3 m 이내(`max_range` 2.95 m)의 사람을 감지하면 됩니다.
- **GPU 여유:** 같은 Orin에서 카메라 3대의 depth 계산이 함께 돌기 때문에, 추론 시간이 YOLO26n 수준이어야 합니다.

## 결과

새 모델은 근거리와 큰 사람에서는 YOLO26n과 비슷하고, 멀리 있는 작은 사람에서는 낮습니다. 전체 AP 차이(−.045)는 대부분 작은 사람에서 나오며, 사용 범위(3 m)에서는 영향이 작습니다. 다만 거리를 가리지 않고 센 감지 수는, 같은 오감지 비율에서 2,563명으로 YOLO26n(3,445명)보다 26% 적습니다.

&#91;embedded content: Jetson AGX Orin 64GB, MAXN, GPU 1300 MHz, TensorRT 10.3, trtexec median · YOLO26n과 DEIM-N 640은 현장 운영 당시 설정인 FP32, 512 모델은 FP16 · \* KD 모델 시간은 graph가 같은 e32로 측정 · 근거리 AP: COCO val2017 사람 중 640 입력 기준 키 100 px 이상\]

| 항목 | YOLO26n (기존) | DEIM-N 640 (1차 학습) | DEIM-N 512 KD (신규) |
| --- | --- | --- | --- |
| 라이선스 | AGPL-3.0 | Apache-2.0 | Apache-2.0 |
| 입력 크기 | 640×640 | 640×640 | 512×512 |
| 전체 AP | .551 | .538 | .506 |
| 근거리 AP (near100) | .736 | .743 | .725 |
| 큰 사람 AP (APl) | .785 | .802 | .792 |
| 작은 사람 AP (APs) | .318 | .292 | .245 |
| Orin 추론 시간 | 3.55 ms (FP32) | 5.66 ms (FP32) | 2.57 ms (FP16) |
| GPU 부하 (15 Hz) | 5.3% | 8.5% | 3.9% |
| confidence threshold | 80 | 83 | 82 |

- 정확도는 COCO val2017 사람 5,000장 기준입니다. 근거리 AP는 키 100 px 이상, 즉 약 3–4 m 이내 사람만 따로 재 값입니다.
- 추론 시간은 Orin(MAXN, GPU 1300 MHz)에서 trtexec로 재 median입니다. YOLO26n과 DEIM-N 640은 현장 운영 당시 설정인 FP32, 신규 모델은 FP16 기준입니다. 신규 모델 값은 graph가 완전히 같은 이전 버전(e32)으로 쟰습니다.
- threshold 82는 YOLO26n의 80과 오감지 비율이 같아지도록 맞춘 값입니다.
- DEIM-N 640은 정확도가 가장 높지만 Orin GPU 포화로 ZED 재시작이 생겨 현장에서 내렸고, 이후 KD의 teacher로 썼습니다.

## 개발 과정

10월 12일부터 15일까지 4일 걸렸고, RTX 5090 한 대에서 학습한 시간은 모두 합쳐 약 19시간입니다.

&#91;embedded content: 학습에서 배포까지 · 시간은 최종 경로만 표시 (512 단독 학습 5.3시간, KD 비교 실험 4.4시간 제외)\]

1. **모델 선정 (10-12):** 계획상 1순위였던 DEIMv2는 2026년 8월에 비상업 라이선스로 바뀌어 제외했습니다. RF-DETR-N은 FP16에 TensorRT 10.4 이상이 필요해 제외했습니다. Apache-2.0인 DEIM-D-FINE-N을 골랐습니다.
2. **640 입력 학습 (10-12, 4.8시간):** AP .538로 YOLO26n에 근접했습니다. 하지만 Orin에 올리자 GPU가 99%까지 차서 ZED가 재시작됐습니다. Orin 추론 시간은 5.66 ms(FP32)였습니다.
3. **경량화 (10-13):** 변형 12종을 비교한 결과 입력 크기가 가장 큰 변수였습니다. 입력을 512로 줄이고, decoder를 2층으로, 출력 후보를 150개로 줄였습니다. FP16도 함께 적용해 Orin 추론 시간이 5.66 ms에서 2.57 ms로 55% 줄었습니다.
4. **512 입력 재학습 (10-13\~14, 5.3시간):** AP .501에서 더 오르지 않았습니다. 이 버전(e32)을 10-14 오전부터 현장에 올렸고, 반나절 동안 ZED 재시작은 없었습니다.
5. **Knowledge distillation (10-14, 4.5시간):** 640 모델을 teacher로 삼아 512 모델을 다시 학습했습니다. AP는 .506으로 오르고, 같은 오감지 비율에서 찾는 사람 수가 23% 늘었습니다(2,089 → 2,563명). graph는 e32와 같아서 속도도 같습니다.
6. **현장 적용 (10-15):** KD 모델로 교체했습니다.

## 핵심 기법

이번 결과는 아래 네 가지 결정에서 나왔습니다.

| 기법 | 왜 했나 | 효과 |
| --- | --- | --- |
| Knowledge distillation (640 → 512) | 512 모델 재학습이 AP .501에서 더 오르지 않아, epoch을 늘리는 대신 방법을 바꿈 | 같은 구조·속도에서 AP .501 → .506, 같은 오감지 비율에서 찾는 사람 수 +23% |
| Orin 실측 기반 경량화 | backbone이 시간의 50%였고 입력 크기가 가장 큰 변수였음. 재학습 전에 변형 12종의 Orin 비용을 먼저 잰 | 입력 512, decoder 2층, 후보 150개. 같은 FP16 기준 시간 27% 감소 |
| Letterbox 학습 | ZED SDK는 입력을 letterbox로 넣는데, 원래 모델은 stretch로 학습돼 약 2 AP를 잃었음 | 학습 조건을 현장 입력과 맞춤. SDK의 여백 색(128) 차이는 영향 없음을 측정으로 확인 |
| 현장 기준 평가 | 사용 범위가 3 m 이내라 근거리 AP를 주 지표로 삼고, threshold는 YOLO26n과 오감지 비율이 같아지도록 맞춤 | threshold 82 결정, 모델을 같은 정밀도에서 비교 |

- **Augmentation:** DEIM 기본 recipe(Mosaic, MixUp, PhotometricDistort, IoUCrop, HFlip)를 그대로 쓰고, 마지막 4 epoch은 augmentation 없이 학습했습니다.
- **안정화:** 학습률을 절반(2e-4)으로 낮추고 EMA 버그를 고쳐, fine-tune 초기에 AP가 떨어지는 문제를 막았습니다.
- **정밀도 검증:** FP16에서 정확도가 무너지는 변형(LAB fold)은 속도가 빠르더라도 제외했습니다.

## Orin 적용과 호환성 점검

모델 자체에는 호환성 문제가 없습니다. 다만 ZED SDK 5.1.1에 원래 있던 동작 두 가지가 확인됐고, 이는 기존 YOLO26n에도 똑같이 해당합니다. 점검은 SDK 라이브러리 분석과 host 측정으로 했고, Orin에서의 확인은 아직 남아 있습니다.

**적용 설정**

- `custom_onnx_file`: `deim_n_person_s512_d2_kd_q150.onnx`
- `custom_onnx_input_size`: `512`
- `confidence_threshold`: `82.0` (실수로 써야 하며, 정수 `82`로 쓰면 node가 죽습니다)

**점검 결과**

| 항목 | 결과 | 영향 |
| --- | --- | --- |
| 모델 구조 | 현장에서 문제없이 돈 e32와 graph가 node 단위까지 같음 | parsing, engine build, 속도는 이미 검증됨 |
| FP16 실행 | SDK 5.1.1 바이너리 분석상, 설정과 상관없이 custom 모델을 FP16으로 build하는 것으로 보임 | 운영 설정은 FP32였음. 실제 precision은 Orin의 engine 파일로 확인 필요 |
| 다인원 감지 | SDK 5.1.1 출력 해석이 첫 행만 읽음. 5.1.2에서 고친 버그 | 프레임당 최대 1명(최고 score)만 보고되는 것으로 분석됨 |
| TensorRT 10.3 정확도 | 새 weight의 Orin FP16 정확도는 미측정 | 이번 교체로 새로 생긴 유일한 확인 항목 |
| 입력 전처리 | SDK는 letterbox 여백을 회색 128로 채움 (학습은 114) | 정확도 차이 없음 (host 측정) |

다인원 문제가 Orin에서도 확인되면, SDK를 올리지 않고 피하는 방법은 출력을 YOLOv8 형식(`[1,5,300]`)으로 export하는 것입니다. 이 export는 아직 구현하지 않았습니다.

## 남은 과제

Orin에서 확인할 것이 네 가지, 그 결과에 따라 결정할 것이 하나 있습니다. 확인 작업은 모두 읽기 전용이라 Orin 환경을 바꾸지 않습니다.

- [ ] TensorRT 10.3 FP16 정확도 측정: 기준값(AP .507) 대비 −0.005 이내면 통과
- [ ] 2\~3명이 나란히 선 장면에서 프레임당 감지 수 확인 (다인원 버그)
- [ ] 여러 날 운용하면서 ZED 재시작과 crash 기록 확인
- [ ] watchdog `max_attempts` 5 → 50 적용 여부 확인
- [ ] 다인원 버그가 확인되면 `[1,5,300]` export 개발 여부 결정

정확도를 더 올리려면 현장 환경에서 찍은 데이터가 필요합니다. 지금은 COCO 사람 데이터만으로 학습했습니다.
