# ACT 결과 보고 예상 Q&A

Oct 29, 2026 · @tony

결과 보고 발표에서 나올 만한 질문과 답변입니다. 각 답변은 먼저 쉬운 말로 답하고, 필요하면 "기술 보충"에 수치와 근거를 붙였습니다.

## 1. 한눈에 보기

**Q. 한마디로 무엇을 한 건가요?**

정답준  위치를 아는 시범 프로그램이 190번 보여 동작을 보고 배워서, 정답 위치 없이 **카메라 영상과 관절 각도만으로** 빨간 큐브를 집어 왼쪽 표시 위에 놓는 인공지능(ACT)을 시뮬레이터 안에서 학습시켰습니다. 로봇의 동작을 사람이 코드로 짜 주는 대신 시범에서 배우는 방식입니다.

**Q. 얼마나 잘 되나요?**

처음 보는 배치 40번 중 **39번 성공**했습니다. 큐브를 평소 범위에 둔 시험은 19/20, 더 넓게 흩어 둔 시험은 20/20 입니다. 성공했을 때 놓는 위치 오차는 평균 4\~6 mm 입니다.

**Q. 이전보다 무엇이 좋아졌나요?**

시범 100번으로 학습한 이전 모델은 넓은 범위에서 13/20 이었습니다. 바깥쪽에 놓인 큐브의 시범 90번을 더해 다시 학습하니 같은 시험에서 20/20 이 됐습니다. 두 모델은 똑같은 배치 20개로 비교했습니다.

**Q. 진짜 로봇에서도 되나요?**

아직 시뮬레이터 결과입니다. 실물과 같은 제어 소프트웨어를 쓰도록 구성해 두었지만, 실물 적용은 다음 단계입니다(8절 참고).

**Q. 걸린 시간은요?**

추가 시범 90번 수집 34분, 데이터 변환 16분, 학습 약 4시간 23분, 평가 120번 약 3시간입니다. 각 단계는 스크립트로 사람 손 없이 돕니다. 이번에는 학습을 100k step 에서 한 번 멈췄다 이어서 했고, 4시간 23분은 순수 학습 시간입니다.

**Q. 시범은 사람이 한 건가요?**

아니요. 시뮬레이터가 알려 주는 큐브의 정답 위치를 보고 움직이는 프로그램(scripted expert)이 시범했습니다. 학습된 로봇은 정답 위치를 모르고, 카메라 영상과 자기 관절 각도만 봅니다.

**Q. 가장 큰 약점은요?**

큐브가 비스듬히 놓였을 때 손목을 충분히 돌리지 못합니다. 그래서 들어 올린 큐브를 옮기는 도중 떨어뜨리는 실패가 있었습니다(5절 참고).

## 2. 데이터와 시범

**Q. demo 와 episode 는 같은 말인가요?**

네. 시범 한 번(큐브 배치 → 집기 → 놓기)을 녹화한 단위가 episode 하나입니다. 초당 30장(30 Hz)으로 기록했고, 평균 약 16.6초입니다. 평가 때의 한 번은 구분해서 trial 이라고 불렀습니다.

**Q. 데이터는 얼마나 되나요?**

190 episode, 94,574 frame, 시간으로 약 52.5분입니다.

| 묶음 | episode | 큐브 배치 범위 | 합계 시간 |
| --- | --- | --- | --- |
| 기본 범위 | 100 | x·y ±60 mm | 약 27.7분 |
| 바깥 띠 | 90 | x ±60\~100 mm, y ±60 mm | 약 24.8분 |

**Q. 한 장면(frame)에는 무엇이 들어 있나요?**

카메라 이미지 2장(외부 카메라, 손목 카메라, 각 320×240), 현재 관절값 7개(팔 6 + 그리퍼), 그리고 정답 행동(action) 7개입니다. 정답 행동은 "바로 다음 순간에 갈 관절 각도"와 그리퍼 명령입니다.

**Q. 정답이 "다음 순간"의 값이면 미래를 어떻게 알아요?**

예측하는 것이 아니라, 시범을 끝까지 녹화한 뒤 다음 장면의 값을 가져다 붙입니다. 녹화가 끝나면 "다음 순간"은 이미 일어난 일이라 그대로 적으면 됩니다.

**Q. seed 는 무엇이고 왜 고정했나요?**

큐브를 무작위로 놓을 때 쓰는 난수의 시작값입니다. 같은 seed 면 같은 배치가 같은 순서로 나옵니다.

- 수집은 seed 91·301, 평가는 131·171·211·251 을 써서, 평가 배치가 학습 때 본 배치와 겹치지 않게 했습니다.
- 두 모델을 비교할 때는 같은 seed 로 평가해, 똑같은 문제를 풀게 했습니다.
- 이 seed 는 Isaac Sim 내부 기능이 아니라 우리 장면 코드의 설정값입니다.

**Q. 바깥 띠 데이터를 따로 모은 이유는요?**

이전 모델의 넓은 범위 실패 7건이 모두 학습 범위(±60 mm) 밖에서 나왔기 때문입니다. 모방학습 로봇은 본 범위 안에서만 잘 동작하므로, 모델을 바꾸는 대신 데이터 범위를 넓혔습니다.

**Q. 시범이 실패하면요?**

실패한 시범은 저장하지 않고 버립니다. 이번에는 190번 모두 성공해서 버린 것이 없었습니다.

**Q. 데이터는 어떤 형식으로 저장하나요?**

기록할 때는 장면마다 JPEG 사진과 JSON 숫자 파일로 저장합니다. 그다음 학습 프레임워크 LeRobot 의 표준 형식으로 바꿉니다. 숫자는 parquet 표, 카메라는 h264 mp4 영상입니다.

- 기술 보충: 압축 없는 픽셀이면 약 41 GB, JPEG 로 2.7 GB, 영상으로 382 MB 입니다. 연속된 장면은 거의 같아서 영상 압축 효과가 큽니다.

**Q. 그리퍼 정답을 실제 각도가 아니라 명령값으로 기록한 이유는요?**

손가락은 큐브에 막혀 중간 각도(0.506 rad)에서 멈춥니다. 이 값을 정답으로 적으면 로봇은 "여기까지만 닫아라"를 배워 쥐는 힘이 0 이 됩니다. 명령값(끝까지 닫기)을 배우면, 멈춘 각도와의 차이만큼 큐브를 누릅니다.

## 3. 모델과 학습

**Q. ACT 는 어떤 모델인가요?**

카메라 영상과 현재 관절 각도를 보고, **앞으로 약 3.3초 동안의 동작 100개를 한 번에** 내놓는 모방학습 모델입니다(Action Chunking with Transformers). 실행할 때는 그중 앞 50개(약 1.7초)를 씁니다. 공개 프레임워크 LeRobot 0.6.1 의 구현을 그대로 썼습니다.

**Q. 구조를 간단히 설명해 주세요.**

1. **눈(ResNet18)**: 카메라 이미지 2장을 각각 작은 조각 80개(token)로 요약합니다.
2. **상황 파악(Transformer encoder)**: 이미지 조각 160개, 관절값 1개, 보조값(latent) 1개를 함께 보고 장면을 정리합니다.
3. **계획(Transformer decoder)**: "1 장면 뒤", "2 장면 뒤" … "100 장면 뒤" 자리를 맡은 질문(query) 100개가 각자 할 일을 정합니다.
4. **출력(action head)**: 각 계획을 관절 목표 7개로 바꿉니다. 결과는 100×7 입니다.

- 기술 보충: encoder 4층, decoder 1층, 차원 512, attention head 8, 파라미터 약 5,160만 개입니다. 모두 LeRobot 기본값이고, 이미지는 크기를 바꾸지 않고 320×240 그대로 넣습니다.

**Q. 왜 동작을 하나가 아니라 100개씩 한 번에 예측하나요?**

한 번에 하나씩 예측하면 작은 오차가 매 순간 쌓여 금방 엉뚱한 곳으로 갑니다. 여러 동작을 묶어 예측하면 움직임이 부드럽고 일관됩니다. 여기서 동작 하나는 1/30초(기록 한 장면)입니다.

**Q. CVAE 나 latent 는 무엇인가요?**

같은 장면에서도 시범이 여러 방식일 수 있을 때(예: 왼쪽으로 돌기, 오른쪽으로 돌기), 그 "방식"을 숫자 32개(latent z)로 알려 주는 장치입니다. 학습 때만 정답 동작을 보고 만들고, 실제 실행 때는 0 을 넣습니다.

- 이번에는 학습 초반(약 18k step)부터 사실상 쓰이지 않았습니다. 프로그램 시범은 같은 장면이면 항상 같은 방식으로 움직여, 나눌 "방식"이 없었기 때문으로 봅니다.

**Q. 학습은 어떻게 했나요?**

시범 장면 32개를 보고, 모델이 낸 동작과 실제 시범 동작을 비교해, 틀린 만큼 모델을 고칩니다. 이것이 학습 step 하나이고, 20만 번(200k step) 반복했습니다.

- 기술 보충: AdamW, 학습률 1e-5, batch 32, 손실 = action L1 + 10 × KL. 640만 샘플(데이터셋 약 68번 반복). RTX 5090 에서 12.7 step/s, 약 4시간 23분.

**Q. 왜 200k step 인가요?**

같은 시험으로 중간 저장본을 비교했습니다.

| 학습량 | 성공 (seed 131·171·211) | 성공 시 평균 오차 |
| --- | --- | --- |
| 100k | 27/30 | 약 11 mm |
| 140k | 30/30 | 약 7 mm |
| 200k | 29/30 | 약 5 mm |

성공률은 140k 에서 이미 거의 찼고, 놓는 정확도는 200k 까지 계속 좋아졌습니다. 더 늘리면 어떻게 될지는 아직 시험하지 않았습니다.

**Q. 학습 loss 가 낮으면 성능이 좋은 건가요?**

아닙니다. 예전에 loss 가 똑같이 0.028 인 두 모델 중 하나는 제자리에 멈춰 있고, 하나는 8/8 성공한 적이 있습니다. 그래서 성능은 항상 실제로 돌려 보고(rollout) 판단합니다.

**Q. 모델 구조를 바꿀 수 있나요?**

네. 층 수, 크기, 이미지 백본, 예측 길이 등은 설정값으로 바꿀 수 있고, 더 큰 변경은 코드를 고쳐야 합니다. 이번에는 기본 구조를 그대로 썼고, 바꾼다면 다시 학습해야 합니다.

## 4. 평가 방법과 결과 해석

**Q. 성공은 어떻게 판정하나요?**

시간이 끝났을 때 두 조건을 모두 만족하면 성공입니다. 사람이 보지 않고, 시뮬레이터의 정답 위치로 자동 채점합니다.

- 큐브 중심이 왼쪽 표시 중심에서 수평 거리 **35 mm 이내**
- 그리퍼가 열려 있음(큐브를 놓았음)

시범을 모을 때의 성공 기준도 이와 같습니다.

**Q. 시험은 어떻게 구성했나요?**

한 번의 시험(run)은 큐브 배치 10개를 차례로 풀고, 배치마다 70초를 줍니다. 배치는 seed 로 정했습니다.

- 기본 범위(x·y ±60 mm): seed 131, 171
- 넓은 범위(x ±100 mm, y ±60 mm): seed 211, 251

**Q. 결과를 표로 보여 주세요.**

| 모델 | 기본 범위 (20번) | 넓은 범위 (20번) | 성공 시 평균 오차 |
| --- | --- | --- | --- |
| 최종 (시범 190번, 200k) | 19/20 | **20/20** | 4.0–6.0 mm |
| 이전 (시범 100번, 200k) | 19/20 | 13/20 | 넓은 범위 10.5–11.4 mm |

- 기본 범위에서는 두 모델이 같았고, 차이는 넓은 범위에서 나왔습니다.
- 넓은 범위를 큐브 위치로 나눠 보면, 이전 모델은 ±60 mm 안쪽 10/10, 바깥쪽 3/10 이었고, 최종 모델은 양쪽 모두 10/10 이었습니다.

**Q. 오차 4\~6 mm 는 무엇을 잰 거예요?**

성공한 시도에서, 놓인 큐브의 중심과 표시의 중심 사이 수평 거리를 평균 낸 값입니다. 성공 기준(35 mm)보다 훨씬 안쪽입니다. 큐브가 기울었는지는 이 값에 들어가지 않습니다.

**Q. 비교는 공정한가요?**

두 모델을 같은 seed, 즉 **똑같은 큐브 배치**로 시험했습니다. 시험마다 시뮬레이터를 새로 띄워 배치가 정확히 같은 것도 확인했습니다. 평가 배치는 학습에 쓴 배치와도 겹치지 않습니다.

**Q. 20번 시험이면 충분한가요?**

표본이 크지는 않습니다. 19/20 과 20/20 의 차이 같은 것은 의미를 두기 어렵습니다. 다만 넓은 범위의 13/20 대 20/20 은 같은 배치로 짝지어 비교한 것이고, 실패가 모두 학습 범위 밖에서 나왔다는 원인까지 맞아떨어져 신뢰할 만합니다. 더 확실히 하려면 seed 를 늘려 시험하면 됩니다.

**Q. 다시 돌리면 같은 결과가 나오나요?**

배치는 똑같이 나옵니다. 하지만 로봇 제어가 실제 시계 기준으로 돌아서 매번 미세하게 다르기 때문에, 경계에 있는 시도는 결과가 바뀔 수 있습니다.

**Q. 영상으로 볼 수 있나요?**

네. 모든 시도를 외부·손목 카메라 나란히 녹화했고(성공/실패가 파일 이름에 붙음), 대표 장면은 GIF 로 만들어 두었습니다. GIF 위쪽의 "3x" 는 원본 영상 기준 배속이고, GIF 자체는 약 1.33배속입니다.

## 5. 실패와 한계

**Q. 최종 모델은 어떻게 실패했나요?**

40번 중 1번(기본 범위 seed 131, 9번째)입니다. 큐브가 약 −27° 돌아 있었고, 약 18 cm 들어 올린 뒤 운반을 시작하자마자 미끄러져 떨어졌습니다. 로봇은 빈 그리퍼로 표시까지 이동했습니다.

**Q. 왜 떨어뜨렸나요?**

손목을 큐브 방향에 충분히 맞추지 못한 채 잡아서, 모서리 쪽을 어정쩡하게 쥐었기 때문으로 봅니다. 이것이 이번 결과의 가장 큰 약점인 **손목 회전(wrist yaw) 추종**입니다.

- 기술 보충: 여러 모델의 rollout 을 합쳐 보면, 쥐는 순간 손목과 큐브 방향 차이가 20° 미만이면 거의 다(약 99%) 성공했고, 20° 이상이면 약 75\~80% 였습니다(실패가 몇 개 배치에 몰려 있어 참고치). 큐브가 ±40° 이상 돌아 있을 때 차이가 가장 컸습니다(중앙값 약 27°, 다른 구간은 12\~13°).

**Q. 그럼 시범 데이터가 잘못된 건가요?**

아니요. 시범 190번을 전부 확인했는데, 손목은 큐브 방향에 0.3° 이내로 정확히 맞춰져 있었고 잘못 잡은 시범도 없었습니다. 문제는 데이터 설계와 학습 쪽에 있다고 봅니다.

- 큐브는 90°마다 같은 모양이라, 시범은 돌릴 각도를 ±45° 안으로 접었습니다. 그래서 큐브가 44°인지 −44°인지에 따라 정답이 거의 90° 뛰는 경계가 있고, 모델은 그 근처에서 손목 각도 오차가 크게 나왔고, 두 답의 중간을 배웠을 가능성이 있습니다(미확인).
- 큐브 방향은 움직이기 시작할 때 멀리서 작게 보이는 상태(외부 카메라에서 약 7×8 화소, 손목 카메라에서 약 12×12 화소)에서 읽어야 합니다.
- 시범에는 "어긋난 뒤 바로잡는" 예시가 없습니다. 프로그램 시범은 항상 첫번에 정확하기 때문입니다.
- 경계 근처 배치를 더 자주 모았지만, 개선 효과는 확인되지 않았습니다(평가에 경계 배치가 거의 없었음).

**Q. 이전 모델은 어떻게 실패했나요?**

학습 범위(±60 mm) 밖에 놓인 큐브를 제대로 겨냥하지 못했습니다. 큐브 옆에서 그리퍼를 닫거나, 큐브 앞에 내려와 큐브를 밀어내고 넘어뜨렸습니다.

**Q. 로봇 움직임이 끊기지는 않나요?**

약 1.7초마다 아주 짧게(약 0.07초) 멈추는 구간이 있습니다. 로봇이 동작 50개(약 1.7초)를 다 쓴 뒤에야 다음 동작을 받기 때문입니다. 그 1.7초 동안에는 카메라를 다시 보지 않고 정해 둔 대로 움직입니다.

- 기술 보충: LeRobot 의 비동기 추론(async inference)을 썼습니다. 원래는 남은 동작이 절반일 때 미리 다음 계획을 받아 겹치는 구간을 섞도록(새 계획 0.7, 이전 0.3) 설계돼 있습니다. 하지만 서버의 유사도 필터 때문에 미리 보낸 관측이 거의 버려져, 추론의 약 97% 가 동작이 바닥난 뒤에 일어났습니다.
- ACT 원래의 temporal ensembling(매 순간 예측해 겹친 예측을 평균)은 이 경로에서 쓰이지 않습니다. 바꾸는 실험은 아직 하지 않았습니다.

**Q. 왜 그런 실행 방식을 골랐나요?**

다음 단계 모델(GR00T)까지 같은 경로로, 설정만 바꿔 쓰기 위해서였습니다. 무거운 모델의 추론 지연을 흡수하고, 우리 코드는 로봇 연결 부분 하나만 두는 구조입니다. 동작을 매끄럽게 잇는 품질은 기본 설정에 맡긴 셈이고, 이번 분석에서 그 점이 약점으로 드러났습니다.

**Q. 시뮬레이터 결과라서 생기는 한계는요?**

- 시범 프로그램과 자동 채점은 시뮬레이터의 정답 위치를 씁니다. 실물에서는 둘 다 다른 방법이 필요합니다.
- 시뮬레이터 영상과 실제 카메라 영상은 모양·조명·화각이 다릅니다.
- 물리도 근사입니다. 특히 마찰로 쥐는 동작은 실물에서 다시 확인해야 합니다.

## 6. 시뮬레이션과 물리

**Q. 어떤 시뮬레이터와 로봇을 썼나요?**

NVIDIA Isaac Sim 6.1.0 에서 산업용 로봇팔 UR16e, Robotiq 2F-85 그리퍼, 손목의 RealSense D405 카메라를 썼습니다. 장면에는 높이 0.20 m 테이블, 35 mm 큐브 2개(0.2 kg), 놓을 자리 표시 2개가 있습니다.

**Q. "물리 접촉 파지(physical)"는 무슨 뜻인가요?**

그리퍼가 큐브를 **실제 마찰로** 쥐는 방식입니다. 예전에는 손가락이 닿으면 큐브를 그리퍼에 "용접"해 붙였는데, 이러면 대충 닫아도 성공해 실물과 멀어집니다. 이번 결과는 모두 마찰 파지 기준입니다.

**Q. 마찰 파지가 바로 됐나요?**

아니요. 기본 설정으로는 손가락이 큐브를 세게 내리쳐 큐브가 튀어 나가고 손목까지 튀어서 0/10 이었습니다. 그리퍼를 부드럽게 닫고 적당한 힘으로 쥐도록 물리 값을 튜닝해 20/20 을 만들었습니다.

| 항목 | 기본 | 튜닝 후 |
| --- | --- | --- |
| 그리퍼 관절 최대 토크 | 26 N·m | 3 N·m |
| 그리퍼 최대 속도 | 146 °/s | 57 °/s |
| 물리 계산 주기 | 60 Hz | 120 Hz |
| 손가락 패드 마찰 | 지정 없음 | 1.2 |
| 큐브 계산 반복 | 16 | 32 |

**Q. 기본 설정이 실제 그리퍼 사양과 달랐던 건가요?**

그렇게 추정됩니다. 닫히는 속도와 힘의 상한 모두 실물 최대치(150 mm/s, 235 N)보다 컸던 것으로 보입니다(대략 환산). 더 큰 문제는 시뮬레이터가 그리퍼를 "아주 단단한 용수철 모터"로 계산하고, 팔과 하나로 묶여 충격이 손목으로 전해진 점입니다. 실물은 힘을 제어하며 부드럽게 쥐기 때문에, 튜닝 후 값은 실물 범위(20\~235 N, 20\~150 mm/s)에 더 가까운 쪽으로 보지만, 정확히 환산하지는 않았습니다.

**Q. 큐브를 쥐는지는 어떻게 알아요?**

그리퍼에는 항상 "끝까지 닫아라"를 보냅니다. 큐브가 있으면 손가락이 큐브에 막혀 중간에서 멈추고, 그 차이만큼 누르는 힘이 생깁니다. 시범 프로그램은 큐브를 들어 올린 뒤 큐브 높이가 실제로 올라왔는지로 "쥐었다"를 판정합니다.

**Q. 120 Hz, 30 Hz 등 주기가 여럿인데 무슨 차이인가요?**

| 주기 | 무엇 |
| --- | --- |
| 120 Hz | 물리 엔진 계산 |
| 60 Hz | 화면 렌더링, ROS 로 보내는 센서 값 |
| 30 Hz | 시범 기록, 로봇에 동작 명령 보내기 |
| 약 0.6 Hz | ACT 추론 (약 1.7초마다 한 번) |

**Q. 카메라는 어떻게 구성했나요?**

작업 영역을 내려다보는 외부 카메라 1대와 손목 카메라 1대입니다. 둘 다 320×240, 수평 화각 약 87°입니다.

- 해상도를 낮춘 이유는 학습 속도입니다. 640×480 에서는 10만 step 에 10시간 이상 걸리는 속도였고(320×240 은 3.7시간), 다음 단계 모델(GR00T)은 어차피 256×256 으로 줄여 씁니다.
- 실물 D405 의 지원 해상도 목록에는 320×240 이 없어(Intel 공개 프로파일 기준), 실물에서는 640×480 으로 받아 줄여 쓰는 것이 좋습니다.
- depth 영상도 시뮬레이터 렌더러가 만들지만(노이즈 없음), 이번 ACT 는 컬러 영상만 썼습니다.

## 7. 직접 한 일과 가져다 쓴 것

**Q. 모델을 직접 만든 건가요?**

아니요. ACT 모델과 학습 코드는 공개 프레임워크 LeRobot 의 것을 고치지 않고 썼고, 모델 하이퍼파라미터도 기본값입니다(학습은 batch 32, 200k step 만 지정). 성능을 만든 것은 모델 주변의 부분입니다. 시범을 어떻게 만들고, 무엇을 기록하고, 어떤 범위를 보여 주고, 물리를 어떻게 맞췄는지입니다.

**Q. 그럼 직접 만든 것은 무엇인가요?**

| 단계 | 직접 만든 것 |
| --- | --- |
| 시뮬레이션 장면 | 로봇·그리퍼·카메라 조립과 치수 정렬, 마찰 파지 물리 튜닝, 작업 장면, 무작위 배치, 카메라 배치, ROS 연결, 계측 로그 |
| 시범 프로그램 | 집기·옮기·놓기 상태머신 전체(이동 경로, 도착 판정, 실패 복구, 성공 판정) |
| 기록과 변환 | 시범 기록기(recorder), LeRobot 형식 변환기 |
| 로봇 연결 | LeRobot 과 ROS 2 로봇을 잇는 어댑터 플러그인 |
| 자동화 | 수집·변환·학습·평가·녹화 스크립트, 환경 설치 스크립트 |

**Q. 가져다 쓴 것은요?**

Isaac Sim, NVIDIA 의 로봇·그리퍼 모델, ROS 2 와 ros2\_control, MoveIt·cuMotion(경로 계획), LeRobot(모델·학습·추론), PyTorch 입니다. 이 외부 패키지들의 코드는 고치지 않았고, 설정값과 에셋의 물리값만 바꿨습니다.

**Q. 왜 LeRobot 을 썼나요? ROS 와 맞나요?**

LeRobot 은 ROS 와 무관한 학습 프레임워크라, 두 곳을 직접 이었습니다. 기록은 ROS 기록기 → 변환기로, 실행은 LeRobot 의 공식 플러그인 방식으로 연결했습니다. 덕분에 모델을 GR00T 등으로 바꿀 때 설정만 바꾸면 됩니다.

**Q. 어려웠던 점은요?**

대표적인 시행착오입니다.

- **로봇이 멈춰 있는 법만 배움:** 시범 장면의 66% 가 멈춘 장면이라, loss 는 낮은데 로봇이 제자리에서 얼었습니다. 대기 시간을 줄이고 멈춘 구간을 정리해 해결했습니다.
- **그리퍼 방향을 거꾸로 판단:** 열림·닫힘 방향을 잘못 보고 보정들을 넣었다가, 손목 카메라로 직접 확인한 뒤 모두 되돌렸습니다.
- **마찰 파지 0/10 → 20/20:** 그리퍼 물리를 튜닝했습니다(6절).
- **범위 밖 실패:** 데이터 범위를 넓혀 13/20 → 20/20 으로 바꿨습니다.
- **측정 도구의 오류:** 채점 스크립트의 집계 버그, 로봇이 아예 움직이지 않았는데 FAIL 로 채점된 일 등을 찾아 고쳤습니다.

**Q. 그 과정에서 얻은 교훈은요?**

- 추측보다 실측. 모양으로 추론한 값이 실제 물리와 여러 번 어긋났습니다.
- loss 는 성능 지표가 아닙니다. 판단은 로봇을 실제로 돌려 보고 합니다.
- 모방학습 로봇의 능력 범위는 데이터의 범위입니다.

## 8. 실물 적용과 다음 단계

**Q. 실제 로봇에 옮기려면 무엇을 바꿔야 하나요?**

시뮬레이터 자리에 실물 드라이버(UR, Robotiq, RealSense)를 연결합니다. 로봇 연결 어댑터, 기록기, 데이터 형식은 실물과 같은 ROS 토픽·컨트롤러를 쓰도록 만들어 두어 그대로 씁니다. 다만 그리퍼 정답(명령값)을 가져오는 토픽과 sim 시간 설정처럼 sim 전용인 설정 몇 가지는 실물용으로 바꿔야 합니다.

**Q. 시뮬레이터에서 학습한 모델을 그대로 실물에 써도 되나요?**

그대로는 어렵다고 봅니다. 시뮬레이터 영상과 실제 영상이 다르고, 카메라 화각·비율도 다릅니다. 실물에는 외부 카메라가 아직 없습니다. 실물 시범을 모아 다시 학습하거나, 시뮬레이터 데이터와 섞는 것이 현실적입니다.

**Q. 실물 시범은 어떻게 모으죠?**

실물에서는 큐브의 정답 위치를 모르므로 시범 프로그램을 그대로 쓸 수 없습니다. 사람이 작은 리더 팔(OMY L100)을 움직이면 UR16e 가 따라하는 텔레옵으로 모을 계획입니다. 실물 리더로 sim 과 실물 UR16e 를 움직여 보는 데까지는 했고 기록기도 연결해 두었지만, 실물 시범을 모아 학습한 적은 아직 없습니다.

**Q. 실물에서 안전은요?**

- 모델 출력과 로봇 사이에 경로 계획기가 없으므로, 어댑터가 명령당 관절 이동을 0.05 rad 로 제한합니다(관절당 약 1.5 rad/s).
- 텔레옵은 버튼을 누르고 있는 동안에만 움직입니다(deadman).
- 실물 적용 전에는 속도 제한과 작업 영역 점검이 따로 필요합니다.

**Q. 다음에 무엇을 개선하나요?**

| 우선 | 무엇 | 방법 후보 |
| --- | --- | --- |
| 1 | 손목 회전 추종 | ±45° 경계에서 정답이 뛰는 문제 처리, 큐브 주변 해상도·크롭 개선, 어긋났다 바로잡는 시범 추가 |
| 2 | 동작 연결과 보정 | ACT temporal ensembling, 또는 비동기 추론의 유사도 필터 완화·동작 묶음 단축 (재학습 없이 A/B 시험 가능) |
| 3 | 평가 신뢰도 | seed 수를 늘려 더 많은 배치로 시험 |
| 4 | 실물 이전 | 실물 카메라 해상도·화각 맞추기, 텔레옵 시범 수집 |
| 5 | 언어 지시 모델(GR00T) | 사전파지 높이에서 멈추는 실패(14/29) 해결, Real-Time Chunking(RTC) 같은 청크 연결 기법 검토 |

**Q. ACT 다음 모델은 무엇인가요?**

계획은 ACT → 소형 VLA → GR00T N1.7 입니다. VLA 는 "빨간 블록을 왼쪽에 놓아" 같은 말로 지시를 받는 모델입니다. ACT 는 말을 입력으로 받지 않아, 이번에는 과제 하나만 학습했습니다. GR00T 는 같은 파이프라인으로 이미 돌려 보았고(용접 파지 시절 데이터, 과제 3개 14/29), 마찰 파지 데이터로는 아직 다시 모으지 않았습니다.
