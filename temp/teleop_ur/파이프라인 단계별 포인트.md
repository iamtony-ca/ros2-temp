# 파이프라인 단계별 발표 포인트

Oct 29, 2026 · @tony

모델(ACT)은 공개 구현을 그대로 썼고, 성능을 만든 것은 그 주변의 6단계를 직접 만들고 고친 일입니다. 각 단계는 "직접 한 일 → 시행착오 → 기술 포인트 → 발표 한 줄" 순서로 정리했고, 괄호 안 § 번호는 `src/HISTORY.md` 의 절입니다.

## 한눈에

| 단계 | 직접 한 일 | 대표 시행착오 | 핵심 메시지 |
| --- | --- | --- | --- |
| 1. Isaac scene | 로봇 모델 합성·정렬, 마찰 파지 물리 튜닝, 장면·무작위 배치·센서·ROS 연결 | 마찰 파지 0/10 → 20/20 | "붙여 주는" 파지가 아니라 실제 마찰로 쥐는 장면을 만들었다 |
| 2. Scripted expert | 집기·옮기·놓기 상태머신 전체 | 파지 깊이 1/5 → 4/5, 대기 제거 | 시범의 품질이 곧 학습의 한계다 |
| 3. Recorder | ROS 기록기, 정답(action) 규칙 | 그리퍼 정답을 명령값으로 (용접 데이터 모델 0/10) | 무엇을 정답으로 적느냐가 로봇의 힘까지 정한다 |
| 4. Conversion | LeRobot 형식 변환기 | 정지 장면 66% → 얼어붙은 정책 | 환경 분리와 데이터 정합성 검사 |
| 5. ACT training | 학습·이어 학습 운영, 데이터 범위 설계 | 넓은 범위 13/20 → 20/20 | loss 는 성능 지표가 아니고, 범위는 데이터가 정한다 |
| 6. Rollout·scoring | LeRobot↔ROS 2 어댑터, 자동 평가·채점·녹화 | 채점 도구 자체의 버그 여러 건 | 공정한 비교(같은 배치)와 사람 없는 채점 |

## 1단계 — Isaac scene

시뮬레이터(Isaac Sim 6.1.0)와 부품 모델(NVIDIA UR16e·2F-85 USD)은 공식 것을 쓰고, 그것을 하나의 로봇으로 조립하고 물리를 튜닝해 작업 장면을 직접 만들었습니다. 핵심 파일은 `ur16e_isaac_ros2.py`(1,875줄)와 `build_ur16e_2f85.py` 입니다.

### 직접 구현

- **로봇 모델 합성:** UR16e 와 2F-85 USD 를 하나의 물리 모델(articulation)로 합쳤습니다. 끝단은 브라켓 → +7 mm → 커플링 +11 mm → 그리퍼로 합계 +18 mm 이고, 이 값을 URDF(MoveIt 쪽)와 USD(Isaac 쪽)에 똑같이 넣었습니다.
- **카메라 브라켓 자세 계산:** PickNik 공칭값(17.1 mm, 6°)으로는 맞지 않아, 메시에 맞는 18.47 mm, 8° 를 구했습니다.
- **마찰 파지 물리(soft 프로파일):** 실행할 때 그리퍼·큐브·물리 설정을 덮어씁니다(아래 표). USD 를 다시 만들지 않아도 인자로 바꿀 수 있습니다.
- **작업 장면:** 높이 0.20 m 테이블, 35 mm·0.2 kg 큐브 2개(마찰 1.2), 표시 2개. 큐브·표시의 정답 위치를 ROS 토픽으로 발행합니다.
- **무작위 배치:** seed 로 고정되는 난수로 리셋마다 x·y·yaw 를 뽑고, 바깥 띠(x 60\~100 mm)와 회전 경계(45° ±10°) 집중 모드를 추가했습니다.
- **센서:** 손목 D405 와 외부 고정 카메라를 배치하고, 실물 D405 와 같은 수평 화각(약 87°)으로 맞췄습니다.
- **ROS 2 연결:** 관절·두 카메라용 연결 그래프 3개를 구성하고, 토픽·좌표계 이름을 실물 드라이버와 같게 맞췄습니다.
- **계측:** step 마다 관절·그리퍼·TCP·큐브를 기록하는 `--grasp-log`, 쥐고 있는지 알려 주는 `/scene/grasp_active`, 그리퍼 폭주를 끊는 가드.

| soft 프로파일 | 원래 | 튜닝 후 |
| --- | --- | --- |
| 그리퍼 관절 최대 토크 / 최대 속도 | 26 N·m / 146 °/s | 3 N·m / 57 °/s |
| 그리퍼 강성 / 감쇠 (per deg) | 20 / 1 | 0.5 / 0.02 |
| 물리 계산 주기 | 60 Hz | 120 Hz |
| 패드 마찰 | 없음 | 1.2 |
| 큐브 계산 반복 | 16 | 32 |

### 시행착오

- **마찰 파지가 0/10 (§16, §53):** 용접 없이 닫으면 손가락이 최고속으로 내리쳐 큐브가 튀고 손목이 2\~3 rad/s 로 튀었습니다. 팔과 그리퍼가 한 물리 모델이라 충격이 손목으로 전해진 것이 원인이었고, soft 프로파일로 **20/20**(비켜 잡기 10/10, 눌러 놓기 10/10, 손목 튀 0)이 됐습니다.
- **그리퍼 방향 오진 (§26 → §28–29):** "Isaac 에셋은 열림·닫힘이 반대"라고 잘못 판단해 보정을 넣었고, 그 결과 없는 문제 세 개를 고치려 했습니다. 손목 카메라로 0/0.4/0.8 개도를 직접 확인한 뒤 보정을 모두 지웠습니다.
- **그리퍼가 큐브를 뚫고 닫힘 (§33, §35):** 링크 원점을 패드로, 힘 평형점을 접촉점으로 잘못 봤습니다. 명령값을 스위프해 실제 접촉점(0.50)을 재고, 마찰 파지에서는 0.8 로 한 번에 닫아 힘으로 쥐게 했습니다.
- **손가락 충돌 모양:** 그리퍼가 큐브까지 내려가지 못하자 "기본 충돌 근사(convexHull)가 손가락 안쪽을 메운다"고 보고 convexDecomposition 으로 바꿨지만, 효과가 없어 가설을 기각했습니다(§26.4). 설정은 남아 있지만 효과가 확인된 수정은 아니고, 마찰 파지 0/10 → 20/20 비교의 양쪽 모두 같은 설정이었습니다.
- **메시 단위:** 커플링·브라켓 메시를 변환하면 기본 단위(cm) 때문에 100배로 커져, 미터 단위 옵션을 켜서 해결했습니다.
- **첫 기동의 셰이더 컴파일 (§52):** 약 3.5분 동안 `/clock` 이 없어 컨트롤러가 전멸했습니다. 실제 `/clock` 을 기다리도록 하네스를 고쳤습니다.

### 기술 포인트

- 시뮬레이터의 그리퍼는 "단단한 용수철 모터"라, 실물처럼 힘을 제어하며 쥐는 동작을 물리 값으로 흉내 내야 했습니다. 원래 값은 속도·힘 모두 실물 2F-85 최대치(150 mm/s, 235 N)보다 컸던 것으로 보이고, 튜닝 후 값은 실물 범위(20\~235 N, 20\~150 mm/s)에 더 가까운 쪽입니다. 정확한 환산은 하지 않았습니다.
- 물리 120 Hz, 렌더·ROS 60 Hz 로 접촉만 촘촘하게 계산했습니다. 대신 headless 실행 속도가 실시간 대비 3.78배에서 약 1.1배로 낮아졌습니다.
- 토픽·좌표계를 실물과 맞춰, 같은 ROS 소프트웨어가 sim 과 실물에서 돕니다.
- depth·point cloud 는 렌더러가 만드는 노이즈 없는 값입니다(ACT 는 컬러만 사용).

> **발표 한 줄:** 공식 시뮬레이터와 부품 모델 위에, 로봇을 조립·정렬하고 실제 마찰로 쥐 수 있도록 물리를 튜닝해 0/10 을 20/20 으로 만들었습니다.

## 2단계 — Scripted expert

시범을 보여 주는 "선생" 프로그램 `pick_place_demo.py`(약 1,280줄)를 직접 만들었습니다. 경로 계획은 MoveIt 과 NVIDIA cuMotion 을 쓰고, 언제 어디로 어떻게 움직일지는 우리 코드가 정합니다.

### 직접 구현

- **상태머신:** READY → 배치 리셋 → DETECT(큐브 위치·방향) → PRE\_GRASP(15 cm 위) → GRASP(직선 하강) → CLOSE → LIFT(20 cm) → TRANSFER → PLACE → OPEN → RETRACT → 판정.
- **이동 방식 분리:** 큰 이동은 MoveIt + cuMotion, 큐브 근처의 접근·후퇴는 5 mm 간격 Cartesian 직선 경로.
- **손목 방향:** 큐브는 90° 대칭이라 회전 각을 ±45° 안으로 접어 가장 적게 도는 방향으로 잡습니다.
- **도착·닫힘 판정:** 실측 위치가 허용오차(정밀 3 mm, 접근 10 mm) 안에 들거나, 0.8초 동안 더 좋아지지 않으면 다음 단계로 넘어갑니다.
- **성공 판정과 복구:** 큐브가 표시에서 35 mm 이내이고 그리퍼가 비어 있어야 저장합니다. 실패하면 그리퍼를 풀고 시작 자세로 복귀해 무인 수집을 이어갑니다.
- **기록기 연동:** 배치가 안정된 뒤 녹화를 시작하고, 성공이면 저장, 실패면 폐기를 부릅니다.
- **cuMotion 로봇 설정 재생성 (§51):** 충돌 구가 메시 안쪽에 있어 최대 39 mm 가 튀어나와 있었고, 자기충돌을 210건 중 49건 놓쳤습니다. 덮는 구로 다시 만들어 놓침 5건이 됐습니다.

### 시행착오

- **SUCCESS 인데 팔이 안 움직임 (§25):** 그리퍼 좌표계가 MoveIt 모델에 없어 목표가 "이미 도착"으로 처리됐습니다. 좌표계를 추가하고, 시작할 때 검사합니다.
- **큐브를 치거나 밀기 (§16, §25):** 처음엔 큐브를 46 cm 날렸고, 관절 공간 하강은 21 mm 밀었습니다. 직선 경로로 바꾸고, 경로 검사가 꺼져 있던 설정(`jump_threshold=0`)을 5.0 으로 고쳤습니다.
- **도착 전에 완료 보고 (§25):** 컨트롤러가 먼저 끝났다고 알려 어긋난 위치에서 하강했습니다. 실측 대기와 하강 직전 재조준을 넣었습니다. (자세 허용오차를 조였다가 5연속 실패로 되돌린 오진 포함)
- **파지 깊이 (§25, §34):** 큐브 중심을 겨냥하면 손끝이 테이블에 닿았습니다. 손가락 최하단이 패드 중심보다 19 mm 아래라는 것을 확인해 +15 mm 로 정했고, 성공률이 1/5 → 4/5 가 됐습니다.
- **불필요한 대기 (§32):** 남는 7 mm 오차를 기다리느라 사이클의 24% 가 대기였습니다. "개선이 멈추면 넘어가기"로 바꾸어 기록된 정지 장면이 65.8% → 8.4% 로 줄었습니다.
- **PhysX 속도 오보고 (§53.4):** 멈춘 손가락을 0.995 rad/s 로 보고해, 닫힘 완료를 모르고 매번 15초를 기다렸습니다. 위치 기준 판정으로 바꿔 닫기가 0.8초로 일정해졌습니다.
- **실패 후 진행 불가와 가짜 성공 (§25):** 그리퍼가 물린 채 남아 수집이 멈추거나, 떨어진 큐브가 "성공"으로 판정됐습니다. 자동 복구를 넣고 판정 기준을 60 → 35 mm 로 줌혔습니다.

### 기술 포인트

- 시범은 사람이 아니라 정답 위치를 아는 프로그램이라 무인으로 대량 수집이 됩니다. 190번 모두 성공, 한 사이클 약 23초, 100개에 약 40분입니다.
- 시범 품질이 곧 학습의 한계입니다. 멈춘 구간, 어긋난 하강, 불필요한 대기는 그대로 학습되므로 시범 단계에서 고쳤습니다.
- 반대로, 항상 한 번에 정확한 시범이라 "어긋난 뒤 바로잡는" 예시는 없습니다. 이것이 손목 회전 약점의 후보 원인 중 하나입니다.
- 실물에서는 정답 위치를 모르므로 이 선생은 sim 전용이고, 실물 시범은 텔레옵으로 모을 계획입니다.

> **발표 한 줄:** 사람 없이 시범 190번을 모두 성공시키는 선생 프로그램을 만들었고, 시범 품질(파지 깊이, 직선 경로, 대기 제거)을 다듬는 것이 학습 결과로 이어졌습니다.

## 3단계 — Recorder

시범을 학습 데이터로 기록하는 ROS 2 노드 `il_recorder.py`(475줄)를 직접 만들었습니다. LeRobot 의 기록 도구는 로봇을 시리얼로 직접 제어하는 구조라 ROS 2 로봇에 맞지 않았고, ROS 의 rosbag2 는 episode 구분·성공 표시·30 Hz 정렬을 따로 만들어야 해서 쓰지 않았습니다.

### 직접 구현

- **기록 방식:** sim 시간 기준 30 Hz 타이머가 카메라 2대, 관절값, 그리퍼 명령의 최신값을 집습니다(보간 없음). 기록된 간격은 모두 0.0333초로 일정했습니다.
- **state (7개):** 팔 관절 6개 + 그리퍼(0\~1 정규화).
- **정답 action (7개):** 팔은 녹화가 끝난 뒤 "다음 장면의 관절값"을 붙이고(`next_state`), 그리퍼는 Isaac 에 보낸 명령값을 씁니다.
- **raw 형식:** 장면별 JPEG, 숫자 `data.json`, 기록 방식을 적은 `meta.json`. 시작·저장·폐기 서비스와 상태 토픽을 둠니다.
- **장치 무관 설계:** 프로그램 시범, 리더 팔 텔레옵, 손으로 끄는 시범 모두 같은 기록기로 기록합니다.
- **안전장치:** 카메라·관절·그리퍼 명령이 없거나, 파지 모드가 다르거나, 그리퍼 정답을 실제 각도로 적으려 하면 녹화를 거부합니다. 10 장면 미만이거나 action 이 빈 episode 는 지웁니다.

### 시행착오

- **용접 데이터 모델이 마찰 파지에서 0/10 (§53.6–53.7):** 용접 시절 시범은 그리퍼를 접촉 직전(0.52)까지만 닫아, 그걸 배운 모델은 쥐는 힘이 0.3\~0.9 N·m 에 그쳤습니다. 또 실제 각도를 정답으로 쓰면 큐브에 막힌 값(0.506 rad)을 배워 쥐는 힘이 0 이 됩니다. 그래서 그리퍼 정답을 **명령 토픽**에서 가져오게 바꾸고 다시 수집했습니다(100/100).
- **리더 토픽 기록 사고 (§49):** 매핑 전 리더 토픽을 기록하면 관절 이름이 달라 action 이 전부 비었는데도 "저장 성공"이 떴습니다. 이제 기록기가 시작을 거부합니다.
- **정지 장면 66% (§31):** 시범 프로그램의 대기 구간이 그대로 기록돼 모델이 "멈춰 있기"를 배웠습니다. 기록 시작 시점을 배치 안정 뒤로 옮기고 대기를 줄여, 최종 데이터는 정지 비율이 약 10\~12% 입니다.
- **numpy 충돌 (§27):** ROS 쪽 numpy 1.26 과 ML 환경 numpy 2.2 가 달라 한 프로세스에서 이미지 변환 라이브러리가 코어 덤프를 냈습니다. 기록(ROS)과 변환(ML)을 두 단계로 나눈 이유입니다.

### 기술 포인트

- 정답은 "미래를 예측"하는 것이 아니라, 다 녹화한 뒤 다음 장면 값을 붙이는 것입니다. 장치에 상관없이 "실제로 간 다음 자세"는 항상 있어서 이 방식을 골랐습니다.
- 그리퍼 정답은 이진값(열기 0, 닫기 1)이고, 실제 각도(state)는 최대 0.63 에서 멈춥니다. 이 차이가 쥐는 힘입니다.
- 무엇을 정답으로 적느냐가 학습 후 로봇이 낼 수 있는 동작을 정합니다.

> **발표 한 줄:** ROS 2 로봇용 시범 기록기를 직접 만들었고, "그리퍼 정답을 명령값으로" 같은 기록 규칙 하나가 0/10 과 성공의 차이를 만들었습니다.

## 4단계 — Conversion

raw 기록(JPEG + JSON)을 LeRobot 표준 데이터셋으로 바꾸는 변환기 `raw_to_lerobot.py` 를 직접 만들었습니다. LeRobot 의 데이터셋 API 는 고치지 않고 불러 씁니다.

### 직접 구현

- **변환기:** 숫자는 parquet 표, 카메라는 h264 mp4 로 묶고, 특징 정의(state 7, action 7, 이미지 2)와 관절 이름을 적습니다.
- **사전 점검(`--dry-run`):** episode 수, frame 수, 과제 문장을 미리 보여 줍니다.
- **정합성 검사:** 파지 모드나 그리퍼 기록 방식이 다른 episode 가 섞이면 변환을 거부합니다.
- **정지 구간 자르기(`--max-idle-run`):** 연속된 멈춤 장면을 지우지 않고 짧게만 남겨 30 Hz 등간격을 유지합니다.
- **두 묶음 합치기:** 기본 범위 100개와 바깥 띠 90개를 복사 없이 symlink 190개로 엮어 한 번에 변환했습니다.
- **변환 하네스:** 수집이 끝나길 기다렸다가 변환하고, 결과 파일로 성공을 판정합니다.

### 시행착오

- **얼어붙은 정책 (§31):** loss 0.028 인 ACT 가 큐브 위에서 180초 동안 멈춰 있었습니다. 데이터의 66% 가 정지 장면이라 "움직이지 마"가 다수 정답이었던 것입니다. 변환 단계에서 정지 구간을 짧게 자르니 같은 loss 로 8/8 이 됐습니다. 이후 시범 단계에서 대기를 줄여, 최종 데이터는 자르지 않고 그대로 썼습니다.
- **해상도와 공유 메모리 (§24, §27):** 640×480 에서는 학습 데이터 로더가 공유 메모리(64 MiB)를 넘어 간헐적으로 죽고, 학습에 10시간 이상 걸렸습니다. 320×240 으로 바꿔 약 70분으로 줄였습니다.
- **코덱 선택과 오진 (§45):** GR00T 학습이 느린 원인을 AV1 디코딩으로 봤지만, 실제로는 CPU 스레드 과다 할당이었습니다(스레드 8개로 처리량 2배). 코덱은 그래도 h264 crf 23 을 기본으로 두었습니다. AV1 과 크기·화질이 비슷하고 어디서나 디코딩되기 때문입니다.

### 기술 포인트

- **두 단계 분리:** ROS 환경에는 torch·LeRobot 을 넣지 않고(시스템 오염, numpy 충돌), 변환은 분리된 ML 환경에서 합니다.
- **크기:** 압축 없는 픽셀이면 약 41 GB, JPEG raw 2.7 GB, 최종 데이터셋 382 MB(190 episode, 94,574 frame)입니다.
- **압축의 대가:** 학습은 압축했다 푼 이미지로, rollout 은 카메라 원본으로 합니다. crf 23 은 그 차이가 작은 설정입니다.
- **메타데이터:** `info.json`(형식·열 정의), `stats.json`(정규화 통계), episode 색인(어느 영상의 몇 초부터인지)을 LeRobot 이 함께 만듭니다.

> **발표 한 줄:** ROS 기록을 LeRobot 표준 형식으로 잇는 변환기를 만들었고, 데이터 구성(정지 장면 비율) 하나가 "멈춘 로봇"과 "8/8 성공"을 갈랐습니다.

## 5단계 — ACT training

ACT 모델과 학습 코드는 LeRobot 0.6.1 그대로이고, 모델 하이퍼파라미터도 기본값입니다. 우리가 한 일은 **어떤 데이터를 얼마나, 어떻게 학습시킬지** 정하고, 학습을 안전하게 운영한 것입니다.

### 직접 구현

- **학습 하네스:** 데이터셋 검사, 워커 수 자동 폴백(4 → 2 → 0), 실패 판정.
- **이어 학습 운영:** `lerobot-train --resume` 으로 100k 에서 멈춘 학습을 200k 까지 이었습니다.
- **데이터 삭제 방지:** 출력 폴더 없이 실행하면 멈추고, 지울 수 있는 경로를 제한하는 가드를 넣었습니다.
- **데이터 범위 설계:** 학습 범위 밖 실패를 보고 바깥 띠 90 episode 를 설계·수집했습니다.
- **학습 설정:** batch 32(기본 8), 200k step(기본 100k). 그 외는 기본값입니다.

### 시행착오

- **ACT 는 언어를 받지 않음 (§30):** 과제 3개(빨강·파랑·다른 표시)를 섞어 학습하면 같은 장면에 정답이 세 개가 됩니다. 섞은 학습을 폐기하고, 과제 하나에 무작위 범위를 넓히는 방향으로 바꿨습니다.
- **loss 는 성능 지표가 아님 (§31, §38):** loss 0.028 인 두 모델 중 하나는 멈춰 있고 하나는 8/8 이었습니다. 100 episode 모델은 loss 가 오히려 높았는데 9/10 이었습니다.
- **데이터 양 (§36, §38):** 50 → 100 episode 로 7/10 → 9/10, 오차 13.4 → 7.6 mm. 범위를 줄여 문제를 숨기지 않았습니다.
- **학습량 (§54.6):** 60k → 200k 로 17/20 → 19/20, 오차 약 12 → 6 mm. 처음엔 "마찰 파지가 오차를 줄였다"고 해석했지만, 같은 60k 끼리는 비슷해 학습량 효과로 정정했습니다(§58.4).
- **데이터 범위 (§58):** 이전 모델의 넓은 범위 실패 7건이 모두 ±60 mm 밖이었습니다. 바깥 띠를 더해 13/20 → 20/20 이 됐습니다. 다만 회전 경계 집중 수집으로 손목 회전 추종이 좋아지지는 않았습니다.
- **운영 사고 (§39, §58.2):** 실행 중인 스크립트를 편집해 학습이 57k 에서 0 으로 돌아간 일이 있었습니다. 이후 "실행 중 편집 금지"와 삭제 가드를 규칙으로 두었습니다.

### 기술 포인트

- 학습 1 step = 시범 장면 32개로 예측·비교·수정 한 번. 200k step = 640만 샘플, 데이터셋 약 68번. RTX 5090 에서 12.7 step/s, 약 4시간 23분.
- 중간 저장본 비교: 100k 27/30(약 11 mm), 140k 30/30(약 7 mm), 200k 29/30(약 5 mm). 성공률은 일찍 차고, 정확도는 끝까지 좋아졌습니다.
- CVAE(시범 "방식" 요약 장치)는 약 18k step 부터 사실상 쓰이지 않았습니다. 프로그램 시범은 방식이 하나뿐이기 때문으로 봅니다.
- 모델 구조(층 수·백본·예측 길이)는 설정으로 바꿀 수 있지만, 이번에는 데이터로 해결할 수 있는 문제를 먼저 풀었습니다.

> **발표 한 줄:** 모델은 그대로 두고 데이터의 양·범위와 학습량을 설계해 성능을 올렸고, loss 가 아니라 실제 평가로 판단했습니다.

## 6단계 — Rollout·scoring

학습된 정책이 로봇을 직접 움직이게 하고, 사람 없이 채점·녹화하는 단계입니다. 추론 서버·클라이언트는 LeRobot 의 async inference 를 그대로 쓰고, 그 주변을 직접 만들었습니다.

### 직접 구현

- **로봇 어댑터 `lerobot_robot_ur16e_ros`:** ROS 와 무관한 LeRobot 과 ROS 2 로봇을 잇는 플러그인입니다. 카메라·관절 토픽을 LeRobot 관측으로 바꾸고, 동작을 컨트롤러 명령으로 보냅니다. 명령당 관절 이동은 0.05 rad 로 제한합니다. LeRobot 의 공식 플러그인 방식이라 LeRobot 코드는 한 줄도 고치지 않았습니다.
- **평가 하네스:** run 마다 Isaac 을 seed 로 새로 띄우고, trial 마다 큐브 리셋 → 시작 자세 → 정책 실행(70초) → 채점을 반복합니다.
- **자동 채점:** 시뮬레이터 정답 위치로 "큐브가 표시에서 35 mm 이내 + 그리퍼 열림"을 판정합니다.
- **녹화와 로그:** 외부·손목 카메라를 나란히 녹화하고(sim 시계 기준, 성공/실패가 파일 이름에 붙음), step 마다 관절·큐브 위치를 남겨 실패를 분석합니다.
- **정리 스크립트:** 이 워크스페이스 프로세스만 골라 종료하고 CLEAN/LEFT 로 판정합니다.

### 시행착오

- **색이 뒤집힌 입력 (§27):** ROS 쪽 numpy 와 충돌해 이미지 변환 라이브러리를 쓸 수 없어 직접 디코딩했습니다. 이때 BGR 로 넣으면 정책은 돌지만 색이 뒤집힌 입력을 받는 "조용한 실패"가 되므로 RGB 로 맞췄습니다.
- **팔이 안 움직였는데 FAIL 로 채점 (§44):** 스트리밍 컨트롤러가 뜨지 않아 팔이 0° 도 움직이지 않았는데 정책 실패로 집계됐습니다. 컨트롤러를 띄우는 launch 를 하네스에 넣고 상태를 검사합니다.
- **채점 도구 버그 (§31, §36):** 시작 자세로 리셋하지 않아 분포 밖에서 시작했고, 카운터 재사용으로 7 성공이 "1/10" 으로 찍혔고, 오래된 로그를 집계했습니다. 하나씩 고쳤습니다.
- **빈 파지로 본 실패가 사실은 미끄러짐 (§54.6):** 로그의 큐브 높이를 보니, 실패 전부 큐브를 쥐고 2\~19 cm 들었다가 미끄러진 것이었습니다.
- **끊기는 실행 (이번 분석):** 추론의 약 97% 가 동작이 바닥난 뒤에 일어났습니다. 서버의 유사도 필터가 미리 보낸 관측을 버려, 겹친 구간 섞기가 거의 일어나지 않았습니다. 그래서 약 1.7초마다 짧게 멈추고, 그동안은 카메라를 다시 보지 않고 움직입니다.
- **CPU 추론 (이번 분석):** LeRobot 기본값 때문에 ACT 는 GPU 가 아니라 CPU 로 추론했습니다(chunk 당 약 60 ms). 인자 하나로 GPU 로 바꿀 수 있습니다.

### 기술 포인트

- **async inference 를 고른 이유:** 다음 단계 모델(GR00T)까지 설정만 바꿔 쓰고, 무거운 모델의 추론 지연을 흡수하며, 우리 코드는 어댑터 하나만 두기 위해서였습니다. 그 대가로 ACT 고유의 매끄러운 연결 방식(temporal ensembling)은 쓰지 못했습니다.
- **공정한 비교:** 두 모델을 같은 seed(같은 배치)로 평가하고, 평가 seed 는 수집 seed 와 다르게 둬습니다.
- **대표 결과:** 최종 모델 기본 범위 19/20, 넓은 범위 20/20(이전 13/20), 평균 오차 4\~6 mm. 12 run(120 trial)에 약 3시간.
- **다음 개선 후보 (재학습 불필요):** GPU 추론, temporal ensembling 실행 루프, 유사도 필터 완화의 A/B 평가.

> **발표 한 줄:** LeRobot 과 ROS 2 로봇을 잇는 어댑터와 사람 없는 평가·채점 환경을 만들었고, 채점 도구의 오류까지 걸러내 결과를 믿을 수 있게 했습니다.
